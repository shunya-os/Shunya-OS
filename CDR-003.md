### 4. Consumer Dependency Graph

```
api/event-bus.ts (LEGACY — to be removed)
  ├── api/use-ai-presence.ts     (imports eventBus, calls eventBus.emit('ai:insight', ...))
  ├── api/use-query.ts           (imports eventBus, calls eventBus.emit() + eventBus.on())
  └── api/use-realtime-sync.ts   (imports eventBus, calls eventBus.emit())

lib/event-bus.ts (DEAD — to be removed immediately)
  └── Zero consumers — confirmed

runtimes/event-bus.ts (CANONICAL — remains)
  └── 14 consumers (all runtimes + 3 API hooks that also import this)
```

**Key insight:** The 3 API hooks already import BOTH event buses. They import `eventBus` from `./event-bus` (legacy) AND `bus` from `../runtimes/event-bus` (canonical). The migration is: drop the legacy import, use the canonical import.

```
  - Change import + rename eventBus → bus

```

### 8. Candidate Approaches

**Approach A: Direct migration (RECOMMENDED)**
Change import + rename method in 3 hooks. Remove both legacy files.
- + Simplest: 3 files edited, 2 files removed
- + No new abstractions
- + All 3 hooks already import canonical bus
- − Requires renaming ~5 `eventBus.emit` calls to `bus.emit`

**Approach B: Re-export legacy from canonical**
Keep `api/event-bus.ts` as a re-export of `runtimes/event-bus.ts`.
- − Creates compatibility layer (forbidden by CEP authorization)
- − Keeps dead path alive
- − REJECTED: violates "no temporary compatibility layer"

**Approach C: Separate adapter**
Create an adapter that maps legacy API to canonical.
- − Violates Simplicity Rule §4
- − REJECTED: unnecessary abstraction
