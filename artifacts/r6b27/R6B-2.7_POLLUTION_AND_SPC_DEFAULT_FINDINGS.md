## §8 — Production test pollution

### Exact quantification (read-only)

| Fact | Value |
|---|---|
| `sh_objects` total | 483 |
| `object_type='test'` rows | **344** |
| All 344 belong to | `organization_id=7` (**Panchi Club**), `workspace_id='spc_business'` |
| Creation window | 2026-09-01 → 2026-09-09 |
| Rows per day | 09-01: 121 · 09-02: 60 · 09-08: 37 · 09-09: 126 |
| Sample names | `Convergence Test Object`, `Get Test`, `Tenant A Object`, `Tenant B Object`, `Cross Tenant Test`, `Cross Delete Test`, `Updated Name`, `Org1 Secret`, `Uniquely Findable` |

The row names are verbatim the object names created by
`tests/test_g11_identity_object.py` (and its kernel sibling
`tests/kernel/test_core_kernel.py`) — `object_type="test"`, created through
`ObjectService.create()` with `organization_id=ADMIN_ORG` and, after the R6B-2.5
patch, `workspace_id=_org_workspace_id(ADMIN_ORG)` which resolves to
`spc_business` for org 7.

### Root cause

The test suite was executed **against the production `DATABASE_URL`**
(`postgresql://shunya@localhost:5432/shunya_os`, loaded from `.env` by
`create_app()`), not against an isolated database. The isolates that exist today
were added later:

1. `app/__init__.py::create_app()` imports `load_dotenv()` and defaults
   `SQLALCHEMY_DATABASE_URI` to a **production-like PostgreSQL URL** when
   `DATABASE_URL` is absent. Before the guard, nothing stopped a test that called
   `create_app()` from binding to production.
2. `create_app()` then performs **unconditional writes** — `db.create_all()` and
   `_seed_default_workspaces()` (which `db.session.commit()`s) — with no
   production guard outside `TESTING`.
3. `tests/conftest.py` had no production-URL refusal at the time.

The environment-isolation failure is therefore: **a test/verification harness
that constructs the app without an explicit isolated `SQLALCHEMY_DATABASE_URI`
silently inherited production from `.env`.**

### Cause fix (this commit)

- New canonical guard `app/safety/db_guard.py` — single source of truth:
  `is_production_like()`, `assert_isolated_database()`.
- `tests/conftest.py` now fails closed through the shared guard (no duplicated
  predicate).
- `create_app()` refuses a production-like database under `TESTING` **or** when
  `SHUNYA_REQUIRE_ISOLATED_DB=1` (the certification-script opt-in).
- `scripts/r6b27_migration_certify.sh` / `r6b25_migration_certify.sh` fail closed
  if `DATABASE_URL` contains `:5432/` or `production`, and export
  `SHUNYA_REQUIRE_ISOLATED_DB=1`.
- Regression tests: `tests/test_r6b27_db_isolation_guard.py` (25 tests) — proves
  production URLs are refused before any test can mutate production.

### Deploy-tree pollution (bonus, same root class)

Certification logs were written **inside the git worktree**
(`artifacts/r6b27/migration_certification_*.log`). An untracked log made the
production checkout dirty, and `deploy.sh` step 4 correctly refuses a dirty tree
— which is why CI run **35211533619 (commit `6874e83`) failed the Deploy job**
with `ERROR: Deploying from a dirty working tree is not allowed`.

Cause fix: certification logs are now written to `RUNTIME_DATA_ROOT` (outside the
worktree); `.gitignore` covers legacy in-tree paths.

### Candidate rows + reversible remediation (NOT executed)

The 344 rows are genuine production pollution but are **not deleted or trashed
here**. Pending explicit approval, a reversible remediation is:

```sql

SELECT id, object_id, name, created_at FROM sh_objects
 WHERE object_type='test' AND organization_id=7 AND workspace_id='spc_business'

-- reversible remediation (soft delete — no hard delete, no trash)

```

A dry-run mechanism (`--dry-run`) should be added before any execution. No
execution is authorised by this document.

## §9 — `spc_default`

### Facts (read-only)

| Property | Value |
|---|---|
| `sh_workspaces` row | `id='spc_default'`, `name='Default'`, `workspace_type='personal'`, `created_by='system'` |
| `organization_id` | **NULL** |
| `status` | **NULL** |
| `created_at` / `updated_at` | **NULL** |
| Depends on it | **1** `sh_objects` row: `id=1462`, `obj_2c9477c5`, `Conversation 'Chat #1 v2'`, org=1, active |
| `user_workspaces` | 0 references |
| Other membership tables | absent / not applicable |

### Origin

`spc_default` is **not** produced by `_seed_default_workspaces()` (which seeds
only `spc_business`, `spc_personal`, `spc_custom`). Its NULL `created_at`,
`status`, and `updated_at` prove it was inserted **outside the ORM**, before the
current model defaults — a legacy placeholder. No code in the repository inserts
the literal `'spc_default'` (only documentation and migration `SKIP` messages
mention it).

### Reachability / canonical-model compliance

- It **violates the canonical workspace model**: a canonical workspace must
  belong to an organization (`sh_workspaces.organization_id` is the authoritative
  ownership link used by `assert_object_access`). NULL org means no identity can
  ever be authorised for it → it is **unreachable** and must fail closed.
- It is not NULL-org-reachable through any authorization path.

### Recommended retirement (migration PREPARED, NOT applied)

Removal is **safe** once the single dependent object is re-homed. Order:

1. Re-home `sh_objects.id=1462` to the canonical workspace of its own
   organization (org 1 → `spc_custom` or `spc_personal`, both org 1). This is a
   data decision for the founder; do not invent a mapping.
2. Then delete the `spc_default` workspace row.

```sql
-- step 1 (requires founder decision on the target workspace)
UPDATE sh_objects SET workspace_id = :canonical_org1_workspace WHERE id = 1462;
-- step 2
DELETE FROM sh_workspaces WHERE id = 'spc_default';
```

**Not applied.** Any migration must go through Alembic authority and an explicit
approval; `deploy.sh` runs `alembic upgrade head` automatically, so no unapplied
migration is added to this commit.
