# R6B-2.7 — CONTENTGENERATION vs sh_objects — OWNERSHIP DECISION

**Question (directive §5):** Is `ContentGeneration` (`m6_content_generations`)
(a) a legitimate domain-specific object whose lifecycle is independently
authoritative, or (b) a second representation of a canonical SHUNYA object that
should converge onto `sh_objects`?

**Status: DECIDED as (a) LIGITIMATE DOMAIN RECORD — but with a HARD CONDITION
that is currently UNMET, and therefore NOT certified as a second authority.**

---

## 1. Evidence

### 1.1 What ContentGeneration is

`app/integration/models.py::ContentGeneration` → `m6_content_generations`.

Columns: `identity_id`, `content_type`, `platform`, `prompt`,
`generated_content`, `tone`, `target_audience`, `word_count`, `ai_model`,
`is_favorited`, `status`, `is_deleted`, `created_at`.

It is a record of an **AI content-generation act** — the prompt, tone, target
audience, model and produced body. It has no relationships, no graph
membership, and no workspace placement.

### 1.2 What sh_objects is

`sh_objects` (483 rows in production) holds enterprise graph objects:
`test` (344), `lead` (46), `document` (41), `Customer` (28), `customer` (23),
`Conversation` (1). **There is no `content` / `output` / `artifact` object type.**

`core/object_service.py` is the single canonical writer and lifecycle owner
(`create`, `archive`, `restore`, `trash`, `recover`, `permanent_delete`), and
every method takes `organization_id` and enforces authorization through
`assert_object_access(identity_id, organization_id, workspace_id)`.

### 1.3 The asymmetry

| Dimension | ContentGeneration | sh_objects + ObjectService |
|---|---|---|
| Tenancy stored | `identity_id` only | `organization_id` + `workspace_id` |
| Authorization gate | identity equality | `assert_object_access` (workspace membership) |
| Lifecycle owner | `app/content_studio/routes.py` | `core/object_service.py` |
| Cross-workspace action | possible (no workspace dimension) | impossible |

**Today `ContentGeneration` is a weaker, parallel lifecycle owner for content
with no tenancy. In that form it IS a competing authority and is NOT acceptable.**

---

## 2. Decision

**ContentGeneration remains a domain-specific content-studio record.** A
generated blog post / social caption / press release is an *authoring artifact*,
not an enterprise graph entity; forcing every draft into `sh_objects` would
pollute the universal object graph and change product behaviour (workspace
selection before generation).

**But separation is only legitimate if authorization is equally strong.** The
canonical authorization predicate is:

```
identity X authorized for workspace Z ⟺
    org_members(identity_id=X, organization_id=Y, is_active=true)
AND sh_workspace_memberships(workspace_id=Z, identity_id=X, is_active=true)
AND sh_workspaces(id=Z, organization_id=Y, status='active')
```

For ContentGeneration to satisfy that, it must carry `organization_id` +
`workspace_id` and its lifecycle route must call `assert_object_access`.

---

## 3. Why that cannot be implemented yet — BLOCKER (needs a founder ruling)

`sh_workspace_memberships` has **0 rows in production**, and **nothing in the
codebase ever writes to it**:

```
grep -rn "ShWorkspaceMembership(" app/ core/   -> only the model definition
grep -rln "ShWorkspaceMembership|sh_workspace_memberships" app/ core/
    -> app/authz/workspace_context.py   (read)
    -> app/objects/legacy_models.py     (model)
```

Every caller of `assert_object_access` — `app/objects/routes.py`,
`app/objects/canonical.py`, `app/objects/file_routes.py`, `app/pdf/routes.py`,
`app/automation/service.py`,
`app/production/identity/onboarding_routes.py`, `core/object_service.py` —
therefore **fails closed for every real user in production**.

This is the data blocker already recorded in
`artifacts/r6b25/R6B-2.6_WORKSPACE_AUTH_ARCHITECTURE.md` §5:

> "This is a data blocker, not a code blocker. … populating memberships for
> existing production `sh_workspaces` rows cannot [be done], without a decision
> from you."

Populating memberships requires a **product ruling** that has not been given:
which identities are members of which of the four existing production
workspaces (`spc_business`→org 7, `spc_personal`→org 1, `spc_custom`→org 1,
`spc_default`→org NULL)? Deriving it from `org_members` would be inventing
authorization. **Inventing it is forbidden (fail closed, no synthetic context).**

---

## 4. Consequence for this Window

- The ContentGeneration lifecycle is **correct and safe at the level it
  actually enforces** (identity ownership, no existence disclosure, truthful
  failures, guarded permanent delete).
- It is **NOT certified as a second object authority**, because it does not yet
  carry canonical tenancy.
- Once the workspace-membership ruling lands, the required follow-up is:
  1. add `organization_id` + `workspace_id` (NOT NULL) to
     `m6_content_generations`;
  2. populate them at generation time from the resolved canonical context;
  3. replace the identity-equality check in the lifecycle route with
     `assert_object_access(identity_id, organization_id, workspace_id)`.

This is recorded as an OPEN WINDOW 5 ITEM — not as a PASS.
