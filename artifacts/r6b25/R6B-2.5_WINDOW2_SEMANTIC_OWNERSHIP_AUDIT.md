## 1. The decisive architectural finding

The rule required is:

    identity → organization → AUTHORIZED workspace

I audited the persisted schema to find that authorization relationship. **It does not exist for the
canonical object store.**

Three disjoint workspace tables are live in the same database:

| Table | Key | Owned by | Referenced by |
|---|---|---|---|
| `sh_workspaces` | `varchar(20)` id | `organization_id` (FK → organizations), `created_by` (legacy string) | `sh_objects.workspace_id` (FK) |
| `user_workspaces` | `integer` id + unique `workspace_id varchar(64)` | `owner_identity_id`, `organization_id` (plain int, no FK) | `user_workspace_memberships.workspace_id` (FK) |
| `workspaces` | `integer` id | `tenant_id` (FK → tenants) | — |

Evidence (disposable cluster, read-only):

```
sh_workspaces        : id varchar(20) PK, organization_id int, created_by varchar(64),
                       status, created_at, updated_at
                       -- NO membership table, NO ACL, NO default/selected flag
user_workspaces      : id int PK, workspace_id varchar(64) UNIQUE, owner_identity_id,
                       organization_id int (no FK), status
user_workspace_memberships : workspace_id FK -> user_workspaces.id, identity_id,
                       email, name, role, is_active
```

**The authorization model exists but governs the wrong table.**

- The only identity→workspace authorization in the schema is
  `user_workspace_memberships.identity_id → user_workspaces.id`, created at signup
  (`app/auth_routes.py:506-524`) with `role="owner"` and a generated id `ws_<hex12>`.
- `sh_objects.workspace_id` is a FK to **`sh_workspaces`**, which has no membership, no ACL and no
  selected/default marker.
- Nothing in the repository creates an `sh_workspaces` row from a `user_workspaces.workspace_id`, and
  nothing propagates a membership into `sh_workspaces`.

So for the canonical object path the only persisted ownership information is:

    sh_objects.organization_id                     (tenant)
    sh_workspaces.organization_id                  (which org owns the workspace)
    sh_workspaces.created_by                       (legacy free-text string, "system" for seed rows)

There is **no persisted statement of which workspace a given identity is authorized for**.

**Consequence:** `Workspace.query.filter_by(organization_id=org_id, status="active")
.order_by(Workspace.id).first()` — introduced by the previous Window 2 pass — is deterministic but
**unauthorized**. Your objection is correct and is the blocker.

Note also: `session["current_workspace_id"]` (written by `app/auth_routes.py:501,528`,
`app/workspace/routes.py:80`, `app/for2/routes.py:291`) holds a **`user_workspaces.workspace_id`**
(or, at `for2/routes.py:291`, a `FounderSpace.space_id`). It is **never** an `sh_workspaces.id`, so it
cannot be used as the explicit selection for the object path without a mapping that does not exist.

`OrgMember...first()` is arbitrary organization selection, and §5 of your directive is also unmet.

## 6. Blockers (Window 2 gate NOT passed)

1. **No authorized-workspace relationship exists for `sh_objects`.** Classes E sites 1, 2, 3, 9 select
   a workspace arbitrarily. I deliberately did **not** invent a rule to make them pass, per your
   instruction. This must be resolved by a decision, because it is an architecture/schema question,
   not a code-cleanup question. Two ways forward:
   - **(i)** Persist the authorization: give `sh_workspaces` a membership/ACL (or bridge it to
     `user_workspaces`/`user_workspace_memberships`), then resolve
     `identity → org → authorized workspace` and **fail closed** when there is none. This is a
     schema addition plus migration, and it is the only path that satisfies your gate literally.
   - **(ii)** Declare `sh_workspaces` rows **organization-wide** (your class D) and stop calling it
     "authorized workspace": every org member may use every org workspace. That must be a **stated,
     persisted** organizational property (e.g. an explicit default-workspace column or an explicit
     org-wide marker), not an implicit `.first()`.
   Until one is chosen, sites 1/2/3/9 either stay arbitrary (unacceptable) or hard-fail (breaks object
   creation). I am not choosing this for you.

2. **Organization resolution may also be arbitrary.** `OrgMember...first()` is used by
   `_resolve_org_id` and `_resolve_tenant_id`. Whether that is safe depends on whether multiple active
   memberships per identity are legal — an invariant I could not prove from constraints or tests
   (§3). If they are legal, `.first()` is arbitrary organization selection.

3. **Multi-workspace isolation is unproven.** Your §9 fixture (Org A = A1+A2, Org B = B1, three
   identities each authorized to exactly one) **cannot be constructed meaningfully yet**, because
   there is no persisted per-identity workspace authorization to assert against. This is a direct
   consequence of blocker 1, not a missing test.

4. **First active workspace selection still exists** at `app/production/objects.py`,
   `app/automation/service.py`, `app/production/identity/onboarding_routes.py` and
   `app/objects/routes.py`. `order_by(id).first()` is noted in code as deterministic; it is **not**
   authorization and I am not claiming it as canonicality.
