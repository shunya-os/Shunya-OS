## 1. The three live workspace systems

Three models named `Workspace` exist, in three modules, with three different tables. All three tables
exist in the running schema. They are **not** linked by any foreign key.

| Model module | `__tablename__` | Primary key | Owner columns | Carries identity authorization? |
|---|---|---|---|---|
| `app/objects/legacy_models.py:37` | `sh_workspaces` | `id varchar(20)` | `organization_id` (FK → `organizations.id`), `created_by varchar(64)` | **No** |
| `app/workspace/models.py:188` | `user_workspaces` | `id int` + unique `workspace_id varchar(64)` | `owner_identity_id varchar(64)`, `organization_id int` (no FK) | **Yes — via memberships** |
| `app/production/identity/workspace_model.py:14` | `workspaces` | `id int` | `tenant_id` (FK → `tenants.id`), `slug` | No |

The authorization relationship that exists:

```
user_workspace_memberships
    .workspace_id  FK -> user_workspaces.id
    .identity_id   varchar(64)
    .email         varchar(255)
    .name          varchar(255)
    .role          varchar(30)   -- owner | admin | member | viewer
    .is_active     boolean
    .created_at    timestamptz
```

Verified against the running schema (read-only):

```
sh_workspaces : id varchar(20) PK | name | workspace_type | icon | color | description |
                created_by varchar(64) NOT NULL | organization_id int (FK organizations,
                ON DELETE SET NULL) | created_at | updated_at | status
                Indexes: PK(id), ix_sw_org(organization_id)
                Referenced by: sh_objects.workspace_id -> sh_workspaces.id
                *** no membership table, no ACL, no default/selected marker ***

user_workspaces : id int PK | workspace_id varchar(64) UNIQUE | name | workspace_type |
                  description | owner_identity_id varchar(64) NOT NULL | status |
                  organization_id int (no FK) | created_at | updated_at
                  Referenced by: user_workspace_memberships.workspace_id

user_workspace_memberships : id int PK | workspace_id FK user_workspaces.id |
                  identity_id | email | name | role | is_active | created_at
```

**The seam:** the canonical object store binds `workspace_id` to `sh_workspaces`, but the only
identity→workspace authorization in the schema governs `user_workspaces`. There is no FK, no mapping
column, and no code path that translates between them.

## 4. Classification of `user_workspaces`

**Answer: B — an intended user-facing workspace model.** It is not dead code and not obsolete.

Evidence:

1. Its blueprint is registered and served (`app/__init__.py:794`, `:801-802`, `:905`).
2. It carries the *only* identity→workspace authorization in the schema
   (`user_workspace_memberships` with `role` and `is_active`).
3. It is the target of the signup path (`app/auth_routes.py:492-529`), which provisions a personal
   workspace and an owner membership.
4. It is the target of `session["current_workspace_id"]` resolution (`app/workspace/models.py:330`).

It is **not** (A) obsolete, and **not** (C) an incomplete predecessor of `sh_workspaces` — it is the
more complete model in terms of authorization, while `sh_workspaces` is the model the object store
actually points at. It is not (D): it serves the same conceptual purpose (a container of tenant data),
so keeping both as first-class is the duplication R6B-2.6 must converge, not preserve.

**Consequence:** `user_workspaces` is live, and `sh_workspaces` is authoritative for canonical
objects. Convergence must pick **`sh_workspaces` as the workspace model** (because
`sh_objects.workspace_id` FKs to it) and **carry the authorization relationship over to it** —
i.e. the canonical membership table must key on `sh_workspaces.id`. Adding a *third* authorization
system is prohibited by the directive and is unnecessary.

## 5. Can `user_workspace_memberships` be bridged? — No authoritative mapping exists

This is the decisive finding, and it means the data migration cannot be performed by inference.

- `user_workspaces.workspace_id` values are generated as `ws_<hex12>` (`app/auth_routes.py:507`).
- `sh_workspaces.id` values are `spc_business` / `spc_personal` / `spc_custom` (seeded) or whatever a
  future creator writes, constrained to `varchar(20)`.
- There is **no column** on either table referencing the other, and **no code** that writes one from
  the other.

So there is no persisted, authoritative statement that "user_workspace X is sh_workspace Z". Any
mapping would have to be inferred from string similarity or naming convention — explicitly forbidden
by the directive ("Never guess the mapping by string similarity"). Likewise, deciding which real
identities are authorized for the existing production `spc_*` rows requires reading production data,
which is out of bounds without your authorization.

**This is a data blocker, not a code blocker.** The canonical membership *model* and *resolver* can be
built and certified on the disposable cluster; populating memberships for existing production
`sh_workspaces` rows cannot, without a decision from you.

## 6. Canonical target design (for your approval before implementation)

One authoritative workspace model: **`sh_workspaces`**. Authorization resolved against it.

New canonical table (name indicative): `sh_workspace_memberships`

| Column | Type | Constraint |
|---|---|---|
| `id` | int PK | |
| `workspace_id` | `varchar(20)` | **FK → `sh_workspaces.id`**, NOT NULL |
| `identity_id` | `varchar(64)` | NOT NULL, indexed |
| `role` | `varchar(30)` | NOT NULL, default `member` (`owner`/`admin`/`member`/`viewer`) |
| `is_active` | boolean | NOT NULL, default true |
| `created_at` / `updated_at` | timestamptz | NOT NULL |

Design decisions taken from the directive:

- **Organization is derived, not stored.** `sh_workspace_memberships` deliberately omits
  `organization_id`: `sh_workspaces.organization_id` is the single source of truth, so the membership
  row cannot contradict it. This satisfies §3 ("prefer deriving organization through the canonical
  workspace") and §13 ("if organization_id is stored ... ensure it cannot contradict").
- **Uniqueness:** `UNIQUE (workspace_id, identity_id)`.
- **No free-text ownership** (no `email`/`name` copies; those live on the identity).
- Organization membership remains `org_members` (org ↔ identity, with `role`, `is_active`).

Authorization predicate, expressible as three independently verifiable conditions:

```
identity X is authorized for sh_workspace Z  ⟺
    EXISTS org_members(identity_id = X, organization_id = Y, is_active = true)
AND EXISTS sh_workspace_memberships(workspace_id = Z, identity_id = X, is_active = true)
AND EXISTS sh_workspaces(id = Z, organization_id = Y, status = 'active')
```

Central resolver (single boundary, §6 of the directive):

```
resolve_current_workspace(identity, requested_workspace_id=None)
    -> canonical sh_workspace, or fail closed
```
It validates: identity is an active org member; the workspace id is authorized for that identity;
the workspace belongs to that organization; the workspace is active. All existing helpers
(`_resolve_org_workspace_ids`, media/automation/onboarding call sites) delegate to it and must not
select a workspace themselves.

## 7. Organization membership (directive §4)

The composite unique constraint is `(organization_id, identity_id)` — it prevents duplicate
memberships **within** one organization. It does **not** make `identity_id` globally unique, so it
does not prove one-organization-per-identity. I found no constraint, no check, and no test asserting
that invariant.

Consequences:

- If multiple active memberships per identity are legal (as the schema permits), then
  `OrgMember...filter_by(identity_id=...).first()` in `app/authz/decorators.py::_resolve_org_id` and
  `app/objects/routes.py::_resolve_tenant_id` is **arbitrary organization selection**.
- The canonical organization must therefore also be an explicit selection validated against the
  identity's active memberships, with no `.first()` and no invented default.

**I am not asserting either way.** This needs your ruling as product semantics, because
"one organization per identity" versus "many, one selected" changes the resolver contract.

## 8. Blockers for R6B-2.6 implementation

1. **No authoritative mapping between `user_workspaces` and `sh_workspaces`.** The canonical
   membership model and resolver can be built; existing membership *rows* cannot be migrated without
   guessing. A reconciliation decision is required (§5, §12 of the directive).
2. **Populating authorization for existing production `sh_workspaces` rows requires production data.**
   Which identities are authorized for the existing `spc_*` rows cannot be inferred from the schema.
   This needs your authorization to inspect production, or an explicit decision that these rows are
   re-provisioned per organization.
3. **Organization multiplicity is undecided** (§7). The resolver contract differs depending on the
   answer, so I should not fix it unilaterally.
4. **The third system (`workspaces`, `tenant_id`-keyed) is out of scope but live**; convergence must
   state explicitly whether it is retained, retired, or bridged, or it becomes a fourth source of
   implicit ownership.
