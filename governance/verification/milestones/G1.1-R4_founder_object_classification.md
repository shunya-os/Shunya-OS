## Classification Decision

### A. Genuine founder-specific concepts (keep as-is, no migration needed)

Items 1–8 above are genuinely founder-specific:

- **FounderSpace** — a workspace concept for the founder/AI conversational context. Has no equivalent in the canonical business-object model. It's a collaboration container, not a business entity.
- **FounderObject** — when used as a workspace-object within a founder space, it represents conversations, documents, AI-generated artifacts, and workspace-specific items. These are NOT the same as canonical business objects (Customer, Invoice, etc.).
- **FounderConversation/FounderMessage** — conversational context within founder experience. No canonical equivalent.

### B. Canonical business objects migrated away from FounderObject (already done)

The following are confirmed migrated to `ObjectService` (sh_objects):

| Former path | Canonical path | Status |
|------------|---------------|--------|
| `app/production/objects.py` (FounderObject create) | `ObjectService.create()` → sh_objects | ✅ Migrated (G1.1-R3) |
| `app/objects/canonical.py` (triple-write) | `ObjectService.create()` → sh_objects only | ✅ Migrated (G1.1-R3) |

### C. Read-only migration compat (acceptable)

Item 9 (`app/objects/canonical.py:52-72`) reads from founder_objects as a historical-data fallback. This produces NO writes to founder_objects. It's a read bridge to support legacy data during migration.

## Runtime Proof

### Test: founder_objects are NOT business object authority

The convergence test `test_legacy_stores_are_not_written_by_canonical` in `tests/convergence/test_object_convergence.py` proves:

```python
create_canonical_object(object_id=oid, ..., tenant_id=1)
# → sh_objects count >= 1
# → FounderObject count == 0
# → UOPObject count == 0
```

The canonical object authority (`ObjectService.create()`) writes ONLY to `sh_objects`. Legacy stores are not written.

### Remaining production writers to founder_objects

After audit, the only production writers to `founder_objects` table are:

1. `app/founder/routes.py` — the founder workspace CRUD (genuine founder-specific)
2. `app/upload/routes.py` — document uploads within founder spaces (genuine founder-specific)
3. `app/auth_routes.py` / `app/routes.py` — companion FounderSpace creation (genuine founder-specific)

None of these write canonical business objects (Customer, Invoice, etc.). They write founder-workspace artifacts.

### What this means for canonical ownership

**The founder_objects table is NOT a competing business-object authority.** It stores a different class of entity — founder-workspace artifacts. The canonical business-object authority (`sh_objects` → `ObjectService`) is the sole production write path for business entities. The overlap was resolved in G1.1-R3 when `app/production/objects.py` migrated from FounderObject to ObjectService.
