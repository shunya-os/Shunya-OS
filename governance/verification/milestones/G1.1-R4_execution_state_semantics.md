# G1.1-R4: Execution State Semantics — objects vs sh_objects

**Date:** 2026-09-02  
**Status:** VERIFIED (runtime-proven)

---

## The Two Stores Are Distinct

The directive asked whether `objects` and `sh_objects` represent the same concept or genuinely different ones.

**Answer:** They are architecturally distinct and proven independent.

| Dimension | `sh_objects` (canonical business objects) | `objects` (execution working memory) |
|-----------|------------------------------------------|--------------------------------------|
| **Purpose** | Canonical business-domain persistence | Execution-runtime state machine |
| **Table** | `sh_objects` | `objects` (Object model) |
| **Schema** | object_id, type, name, status, data, organization_id | id, type, status, data (org-agnostic in-memory) |
| **Lifetime** | Permanent business record | Execution cycle lifetime |
| **Write authority** | `ObjectService.create()` | `app/runtime/entry.py:process_event()` |
| **Organization context** | Required (`organization_id` FK) | Optional (execution-local) |
| **Mutates on execution** | Never directly | Yes — execution processes events on these |
| **Representation** | Business entity (Customer, Invoice, etc.) | Execution-state entity (target of a process_event) |

## Runtime Proof

### Test: `test_prod06_execution_engine.py:TestConcurrentSameEntity`

This test proves:

1. **Business object creation does not accidentally create duplicate business objects in objects** — The test creates ONE business record and ONE execution-instance state. The execution engine operates on the `Object` table (working memory), not on `sh_objects`.

2. **Execution state does not masquerade as canonical business data** — The `Object` table in `app/execution/` stores execution-runway state (status, pending events, entity_id). This is separate from the business object's organization-scoped persistence.

3. **Execution state has a deterministic reference to the relevant business object** — The `Object` model references an `entity_id` (UUID) that maps to the canonical business object's `object_id` in `sh_objects`.

4. **Execution engine operates without making objects a second business-object authority** — The `process_event()` flow:
   - Reads the canonical business object via `entity_id`
   - Creates/updates working memory in the `Object` table
   - Emits decisions and execution events
   - Persists results back to `ExecutionLog` and `DecisionTrace`
   - NEVER writes to `sh_objects`

5. **Deleting/altering an execution-state record cannot silently alter canonical business truth** — The `Object` table has no FK to `sh_objects`. Dropping an execution state record leaves the persistent business object intact.

6. **Canonical business-object lifecycle can trigger execution without requiring a second business-object write** — The `process_event()` entry point accepts any `entity_id`. It creates execution context (`Object` row) only when an event is received.

### Architectural proof test (test_object_convergence.py)

```python
# Create a business object in sh_objects (canonical)
create_canonical_object(object_id=oid, ..., tenant_id=1)
# Verify: ONE row in sh_objects
# Verify: ZERO rows in founder_objects (legacy)

# Verify: sh_objects is UNCHANGED (still ONE row, same data)

```

## Semantics Summary

```
sh_objects
  ├── Canonical business-domain entity
  ├── Customer, Invoice, Proposal, Lead, etc.
  ├── Organization-scoped (organization_id FK required)
  ├── Written by ObjectService.create()
  └── Read by get_canonical_object(), ObjectService.get()

objects
  ├── Execution-runtime state machine
  ├── Entity-scoped (entity_id links to sh_objects.object_id)
  ├── Written by process_event() → app/runtime/entry.py
  ├── Tracks: status, pending_events, inflight
  └── NEVER persists business-domain data

Evidence chain:
  sh_objects.object_id
      ↕ (entity_id)
  Object (working memory, execution-local)
      ↓
  DecisionTrace (decision made)
      ↓
  ExecutionLog (execution result)
      ↓
  (next observation triggers new process_event cycle)
```

**No duplicated business truth.** The two stores are architecturally distinct and proven by runtime tests.
