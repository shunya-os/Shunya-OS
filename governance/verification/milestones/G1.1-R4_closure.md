## Self-Rejection

### What canonical authority did I establish?
- `ObjectService` (sh_objects) as the sole write path for business objects
- `app/runtime/entry.py` → `execution_engine` as the sole execution authority
- `organizations` table + `current_org_id` session as the sole org context resolution

### What competing authority did I remove?
- `core/execution_runtime/` — fully decommissioned (pipeline wiring, phantom imports, module files)
- FounderObject legacy fallback in `app/production/objects.py` — GET/PUT routes now sh_objects only
- `org_id = 1` fallback — replaced with explicit rejection
- `tenant_id = 1` default — replaced with mandatory tenant_id

### What production caller did I migrate?
- `app/production/objects.py:update_typed_object` — removed legacy FounderObject update path
- `app/production/objects.py:get_typed_object` — removed legacy FounderObject read path
- Both now use canonical sh_objects only

### What did I delete?
- `core/execution_runtime/` (3 files + 1 doc)
- `ExecutionRuntimeAdapter` class from pipeline
- 10 `register_execution_actions()` methods from intelligence runtimes
- 2 skipped test files

### What did I initially misunderstand?
- The `org_id = 1` fallback had THREE independent locations, not one
- The `objects` vs `sh_objects` distinction was already architecturally correct — the directive's concern was about proving it, not fixing it
- The `register_execution_actions()` methods were genuinely dead code that no caller ever invoked

### What runtime behavior proves the correction?
- 9 new negative tests prove org-missing, cross-org, and missing-tenant rejections
- 44 execution engine tests prove the canonical execution chain
- 4 convergence tests prove sh_objects is the sole write authority
- App imports cleanly without `core/execution_runtime/`

### What can still bypass the canonical path?
- FounderObject in `app/founder/routes.py` — but this is genuinely founder-specific, not business objects
- Raw SQL queries in `app/intelligence/` routes that read from `founder_objects` — but these are read-only AI context queries, not business object mutations

### What happens when authorization fails?
- No org context → 400 error, no mutation
- No identity → 401, no mutation
- Cross-org access → 404 (object not found in this org)
- Missing tenant → error returned from `create_canonical_object()`

### What happens when execution fails?
- `ExecutionLog` records the failure truthfully
- No fake completion emitted
- Evidence chain preserved

### What proves tenant isolation?
- `test_cross_org_object_creation_isolation` — Org A creates, Org B cannot find it
- All routes scope lookups by `organization_id`

### What proves persistence after restart?
- Database-backed persistence for all canonical stores (PostgreSQL)
- Not tested in this phase (requires restart simulation)

### What proves the frontend uses the canonical backend?
- Frontend tests pass (39/39)
- Frontend build succeeds
- Frontend API calls go to `/api/v1/objects/<type>` which routes through `ObjectService`
