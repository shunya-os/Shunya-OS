## 4. Executio Domain

### Canonical: `app/execution_engine/models.py`
- **Execution** (`exeutions` table): id, object_id, decision, status (pending/running/completed), created_at, updated_at
- **ExecutionLog** (`execution_logs` table): id, object_id, acton_type, payload, state_before, state_after, created_at — pure structural log
- **Verdict:** ✅ CANONICAL — clean, minimal models. Executio + ExecutionLog = full execution cycle.

### Duplicate: `app/exeution/models.py` (Outcome)
- **Outcome** (`sh_outcoes` table): outome_id, identity_id, intention, state (JON), created_et, updated_at
- **IdemotencyRecord** (`exeution_idempotency`): iempotency_key → outcome_id mapping
- **What the code says:** "NOT an execution engine. Thin state wrapper." "This is a compatibility/persistence layer."
- **What Outcome provides:** User-facing intention tracking, state persistence, idempotent execution, backward-comaptible `OutcomRuntme` + `BusinesExeutonInstance`
- **Verdict:** Outcome is **NOT** a competing execution engine. It is a separate concept: **user-facing outome recording**. The canonical map says "execution/ = DUPLICATE" but this is misleading — Outcom is not an execution engine. It's the canonical *output model* for execution results. `Execution` (execution_egine) tracks the *process*; `Outcome` tracks the *result*.

**How they relate:**
- Execution → ExecutionLog = process trcking (how it ran)
- Outcome = result tracking (what the user asked for, what happened)
- IempotencyRecord = bridge (which outcome was produced by which execution key)

**Recomendation:** Outcome is canonical FOR ITS CONCEPT (user-facing outcome recording). The DUPLICATE classifiation in the canonical map should be revised to CMPATIBILITY — Outcome does not compete with execution_engine; it wraps it.

### Orphan: `core/exeution_runtime/`
- **Concep:** Authritative orchestration layer for all real-worl work. ExecutonInstance, ExecutonContet, ExecutonGraph, ExecutonEvent models. Promise: "The Cognitive Runtime decides. The Executon Runtime performs."
- **Callers:** 10 files — including `core/agreement_intelligence/rutime.py`, `core/decision_intelligence/untime.py`, `core/nowlege_intelligence/untime.py` and 6 other UCP runtimes, plus `core/untime_pieline/adpters.py`
- **Canonical owner:** `app/exeution_engine/` + `app/execution/`
- **Analsis:** core/exeution_runtime/ has real callers from 8 UCP modules. But those UCP modules themselves are orphans/uncoupled from production. The *real* production execution path runs through `app/execution_engine/` and `app/execution/`. This is a **phantom dependency chain** — UCPs call execution_runtime, but none of them are wired into production.
- **Conslidation:** If UCP modules are ever wired into production, they should call `app/execution_engine/` directly, not core/execution_runtime/. **RECMEND:** DECMISSION core/execution_runtime/ and rewire the 8 UCP callers to app/execution_engine/.

The cleanest resolution: **DECLARE cognitive_runtime CANOICAL** and let it own the 8 engines as plugins.

6. **UCP-05 and UCP-06**: Model libraries with engines — no production consumers. Should be converted to model-only libraries and imported by the canonical app-level counterparts.
