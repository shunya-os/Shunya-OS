### 10. Candidate Implementation Approaches

#### Approach A: Direct `open()` mapping (RECOMMENDED)

Replace `window.location.href = route` with a call to `useWorkspaceStore.getState().open()` using the appropriate `WorkspaceType` for each route target.

**Trade-offs:**
- + Simplest change — single atomic edit
- + Uses already-imported store
- + Pattern already proven (line 93)
- + All 11 targets map to valid WorkspaceType values
- − Requires mapping 11 targets to workspace types (one-time effort)

#### Approach B: `activate()` on existing workspace, `open()` on new

First search for an existing workspace of the target type, activate it if found, open it if not.

**Trade-offs:**
- + More efficient — reuses existing workspaces
- − More complex — two calls instead of one
- − `open()` already handles deduplication internally (creates if absent, activates if exists)
- − No benefit over Approach A for this CEP scope

#### Approach C: New navigation abstraction layer

Create a dedicated `NavigationService` that all components use for navigation.

**Trade-offs:**
- + Formal separation of concerns
- − Violates Constitutional Simplicity Rule (§4) — adds unnecessary abstraction
- − Workspace Runtime already owns navigation
- − REJECTED: additional abstraction without constitutional justification

#### Approach D: Event-bus based navigation

Emit a navigation event on the runtime event bus, and have the Workspace Runtime subscribe to it.

**Trade-offs:**
- + Decoupled
- − Event bus consolidation is CEP-003 (deferred until after constitutional violations are resolved)
- − Premature — the event bus is still being consolidated
- − REJECTED: creates dependency on unconverged infrastructure
