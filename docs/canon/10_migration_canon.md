## 1. Purpose

This document defines the strategy for migrating SHUNYA from its current state to the canonical architecture defined in documents 01-09. **No migrations are generated by this document** — this is the strategy document that governs all future migrations.

---

## 2. Migration Principles

### 2.1 Core Principles

| Principle | Description |
|-----------|-------------|
| **Never break production** | Every migration must be reversible or additive |
| **Strangler fig pattern** | New code grows alongside old; old is removed when unused |
| **Tests before migration** | Canonical test suite must exist before migration |
| **Zero regressions** | All existing tests must pass after every step |
| **Documented decisions** | Every migration decision is recorded in an ADR |
| **Incremental, not big bang** | No single migration touches the entire codebase |
| **Protocol first** | Define the interface, then implement, then swap |

### 2.2 Migration Risk Categories

| Risk | Mitigation |
|------|-----------|
| **Data loss** | Never destructive — always additive or transitional |
| **API breakage** | Versioned APIs; old versions coexist until migration complete |
| **Performance regression** | Performance tests run alongside functional tests |
| **Behavior change** | A/B comparison between old and new implementations |
| **Security regression** | Security audit gates at every phase |

## 3. Migration Strategy

### 3.1 Overall Approach: Strangler Fig

```
Phase 0: Canonical Freeze
    │
    ▼
Phase 1: Core Extraction (core/)
    │
    ├──► Old app/ modules remain → new core/ is built alongside
    │
    ▼
Phase 2: Intelligence Layer (intelligence/)
    │
    ├──► Old intelligence modules remain → new intelligence/ built alongside
    │
    ▼
Phase 3: Experience Layer (experience/)
    │
    ├──► Old experience code remains → new experience/ built alongside
    │
    ▼
Phase 4: Domain Extraction (domains/)
    │
    ├──► Old app/ and sub-apps remain → new domains/ built alongside
    │
    ▼
Phase 5: Cleanup
    │
    ├──► Old code removed only when nothing depends on it
```

### 3.2 The Adapter Pattern

During migration, each old module is wrapped in an adapter that conforms to the new protocol:

```
Old Module ──→ Adapter (implements new protocol) ──→ New Consumers
                    │
                    └──→ (internally calls old module)
```

When the new implementation is complete and tested, the adapter is swapped to call the new module directly:

```
New Module ──→ (remains conformant) ──→ New Consumers
```

Then the old module is removed.

## 5. Phase 1: Core Extraction

### 5.1 Objective

Extract universal runtime code from `app/` into `core/` without changing behavior.

### 5.2 Steps

1. Create `core/` directory structure
2. Extract `app/kernel/` → `core/kernel/` (UniversalObject protocol)
3. Extract `app/temporal/` → `core/timeline/`
4. Extract `app/evidence/` → `core/evidence/`
5. Extract `app/relationship/` → `core/relationship/`
6. Create new core modules: `core/audit/`, `core/event/`, `core/storage/`
7. Create adapter in `app/` that delegates to `core/`
8. Update imports incrementally
9. Run full test suite after each step

### 5.3 What Stays in `app/`

During this phase, `app/` retains:
- All Flask routing
- All domain-specific code
- All CRM models
- All template rendering

### 5.4 What Moves to `core/`

| Module | New Location | Rationale |
|--------|-------------|-----------|
| `app/kernel/` | `core/kernel/` | Universal object protocol is foundational |
| `app/temporal/` | `core/timeline/` | Timeline is a universal capability |
| `app/evidence/` | `core/evidence/` | Evidence is a universal capability |
| `app/relationship/` | `core/relationship/` | Relationship graph is universal |
| New | `core/audit/` | Audit trail is mandatory for all objects |
| New | `core/event/` | Event bus is required by the runtime |
| New | `core/storage/` | Storage abstraction enables backend independence |
| New | `core/search/` | Search interface is mandatory per protocol |

### 5.5 Acceptance Criteria

- [ ] All core modules exist with full test coverage
- [ ] `app/` continues to work (delegates to `core/`)
- [ ] Test suite passes with zero regressions
- [ ] No domain-specific code exists in `core/`

## 10. Data Migration Strategy

### 10.1 Principles

| Principle | Description |
|-----------|-------------|
| **Additive first** | New tables are created alongside old; data is populated from old |
| **Transitional state** | Both old and new tables serve reads until migration is verified |
| **Verifiable** | Migration correctness is verified by comparing old vs new queries |
| **Rollbackable** | Every migration has a defined rollback (drop new tables, keep old) |

### 10.2 Model Migration Approach

```
1. Create new canonical tables alongside old tables
2. Write migration: copy data from old → new with transformation
3. Verify: compare query results from old and new
4. Update application code to read from new tables
5. Monitor: verify production behavior
6. Update write code to write to new tables (dual-write during transition)
7. Verify again
8. Remove old table (after quarantine period)

Old: Write → Old Table → Read from old table
Transition: Write → Old + New Tables → Read from new table
New: Write → New Table → Read from new table
```

### 10.3 Object Model Migration (app/models.py)

Each model in the classification (06 §9) has a specific migration path:

| Classification | Migration Path |
|---------------|---------------|
| **Canonical** | Create canonical table → copy data → verify → swap reads → swap writes → drop old |
| **Refactor** | Create canonical table with canonical schema → transform data → verify → swap |
| **Merge** | Create canonical table → merge data from multiple old tables → verify → swap |
| **Split** | Create multiple canonical tables → split data → verify → swap |
| **Legacy** | Create canonical replacement → migrate functionally → deprecate old |
| **Remove** | Verify no consumers → archive old → remove |

## 11. Model Migration Strategy

### 11.1 UniversalObject Protocol Conformance

Existing models must conform to the Universal Object Protocol (04). The migration path for each model follows this pattern:

```
1. Add mandatory fields (object_id, object_type, version, etc.)
2. Add timeline and audit support
3. Add relationship graph support
4. Add evidence chain support
5. Add AI context
6. Backfill existing data
7. Verify protocol compliance
```

### 11.2 Priority Order

Models should be migrated in this order:
1. Core universal objects (Identity, Human, Organization)
2. Relationship graph
3. Decision/Commitment/Outcome chain
4. Knowledge/Memory/Evidence
5. Workspace/Conversation
6. Document/Task/Workflow
7. FinancialObject
8. Domain-specific extensions

## 12. Testing Strategy During Migration

### 12.1 Test Categories

| Test Type | Purpose | Runs At |
|-----------|---------|---------|
| **Unit tests** | Verify individual component behavior | Every commit |
| **Protocol conformance** | Verify objects implement UniversalObject protocol | Every PR |
| **Integration tests** | Verify modules work together | Every PR |
| **Regression tests** | Verify existing behavior unchanged | Every commit |
| **Compatibility tests** | Verify new and old implementations return same results | Throughout migration |
| **Performance tests** | Verify no performance regression | Each phase |

### 12.2 A/B Testing

During migration, A/B test critical paths:
```
Request → Old Implementation (control)
       → New Implementation (candidate)
       → Compare results
       → Alert on differences
       → Log for analysis
```

## 13. Rollback Strategy

### 13.1 Rollback Levels

| Level | Action | Response Time |
|-------|--------|---------------|
| **Config rollback** | Revert feature flag | Minutes |
| **Code rollback** | Revert to previous deployment | 30 minutes |
| **Data rollback** | Restore from database backup | Hours |
| **Schema rollback** | Run rollback migration | Hours |

### 13.2 Rollback Triggers

- Test failure rate > 5% of suite
- Performance regression > 20%
- P1 bug in migrated code
- Data integrity violation detected
- Security vulnerability discovered

## 14. Risk Management

### 14.1 Risk Matrix

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|-----------|
| Migration breaks production | Low | Critical | Strangler fig pattern, feature flags, rollback plan |
| Data loss during migration | Low | Critical | Additive-first approach, verification checks |
| Performance regression | Medium | High | Performance baseline, A/B testing, monitoring |
| Developer confusion | Medium | Medium | Documentation, clear phase boundaries |
| Scope creep | High | Medium | Phase gates with explicit acceptance criteria |
| Dependency deadlock | Medium | High | Topological sort of module dependencies |

### 14.2 Phase Gates

Each phase has a gate that must be passed before the next phase begins:
1. **Gate review** — governance board reviews phase completion
2. **Test suite** — 100% pass rate on full test suite
3. **Performance** — no regression beyond threshold
4. **Documentation** — phase documentation complete and reviewed
