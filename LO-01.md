# LO-01 — Canonical Living Object Contract

## Permanent implementation contract for all Living Objects in SHUNYA

**Status:** Draft — awaiting founder approval
**Purpose:** Define the complete behavioral contract that every Living Object must satisfy. Not a UI specification. Not a component inventory. An object behavior contract.

---

## I. Canonical Answer

> **A Living Object is anything SHUNYA can observe, reason about, act upon, and remember.**

Every Living Object, regardless of type (Lead, Proposal, Invoice, Contact, Task, Trip, Document, Email, Meeting, Supplier, Customer, or any future object), shares the same behavioral contract. The contract defines what every object:

- **MUST** do (universal capabilities)
- **MAY** do (optional capabilities)
- **CANNOT** do (prohibited patterns)

No object type shall redefine these behaviors. Specialization is achieved through data, not through reimplementation.

---

## II. Universal Capabilities (MUST)

These capabilities are mandatory for every Living Object. No object type may omit them.

| # | Capability | Constitutional Purpose | Required Runtime | Mandatory | Notes |
|---|---|---|---|---|---|
| 1 | **Identity** | Every object must be uniquely addressable and nameable. | Identity Runtime | Yes | `object_id`, `object_type`, `name`, `created_at`, `created_by`. Immutable after creation. |
| 2 | **Reality** | Every object must participate in the Reality Stream. State changes produce Reality Events. | Reality Engine | Yes | Object creation → `object_created` event. State change → `object_updated` event. Evolution → `object_evolved` event. |
| 3 | **Attention** | Every object must be scorable by the Attention Engine. | Attention Engine | Yes | Attention items are produced automatically when an object's state changes in an important way. Priority scoring based on object properties. |
| 4 | **Evidence** | Every claim about an object must be verifiable. | Evidence Runtime | Yes | Every state change carries a confidence score, source, and timestamp. No opaque claims. |
| 5 | **Timeline** | Every object must have a complete history of state changes. | Event Collector | Yes | Events form an append-only log. The Timeline is the ordered sequence of events for a given object. |
| 6 | **Relationships** | Every object must be able to relate to any other object. | Graph Engine | Yes | Edges are typed (parent, depends_on, references, belongs_to, etc.). Bidirectional traversal. No hardcoded relationship schemas. |
| 7 | **Cognition** | Every object must accept AI observations and predictions. | AI Presence Engine | Yes | Observations are generated by Cognition Runtimes. Each has a confidence score, reasoning, and source. The object can have multiple, possibly conflicting observations. |
| 8 | **Lifecycle** | Every object must have a defined lifecycle with stages. | Lifecycle Runtime | Yes | Stages are configurable per object type. Transitions produce events. Current stage is queryable. |
| 9 | **Searchability** | Every object must be findable via natural language search. | Search Runtime | Yes | Content, metadata, relationships, and observations are all indexed. Search returns objects by relevance. |
| 10 | **Permissions** | Every object must have access control. | Permission Runtime | Yes | Owner, viewers, editors. Read/write/admin per identity. Inherited from workspace/org by default. |
| 11 | **Memory** | Every object must remember its past states and interactions. | Reality Engine (Event Store) | Yes | The event log IS the memory. Past states can be replayed. No state is lost. |
| 12 | **Health** | Every object must expose a health or status indicator. | Health Runtime | Yes | Computed from lifecycle stage, recent events, attention items, and observations. Normal / Attention Needed / Critical / Archived. |

## III. Optional Capabilities (MAY)

These capabilities are available to every Living Object but are only activated when constitutionally appropriate. An object type that lacks one of these capabilities is not deficient.

| # | Capability | Constitutional Purpose | Required Runtime | Activation Trigger |
|---|---|---|---|---|
| 13 | **Conversation** | Allow human discussion about the object. | Conversation Runtime | Activated when an object receives its first comment or note. |
| 14 | **Commitments** | Track promises, tasks, and obligations related to the object. | Commitment Runtime | Activated when a commitment is created referencing the object. |
| 15 | **Execution** | Execute automated or manual actions on the object. | Execution Runtime | Activated when the object has an action that can be performed (approve, send, complete, etc.). |
| 16 | **Files** | Attach files to the object. | File Runtime | Activated when the first file is attached. |
| 17 | **Communication** | Associate emails, messages, and notifications with the object. | Communication Runtime | Activated when a communication references the object. |
| 18 | **Predictions** | Generate AI predictions about the object's future state. | Prediction Engine | Activated when sufficient historical data exists for the object type. |
| 19 | **Automation** | Define automated behaviors triggered by object state changes. | Automation Runtime | Activated when a rule is defined for the object type or instance. |
| 20 | **Extensibility** | Allow custom fields, metadata, and behaviors. | Schema Runtime | Activated when a custom field is added. Extensible without code changes. |

---

## IV. Forbidden Patterns (CANNOT)

The following patterns are constitutionally prohibited for all Living Objects:

| Pattern | Why |
|---|---|
| **Hardcoded relationship schemas** | Relationships must be graph edges, not foreign key columns. No object type may define a fixed set of related types. |
| **UI-specific state** | Objects may not hold UI state (visibility, scroll position, animation state). |
| **Duplicate identity** | No two objects may share the same `(object_type, object_id)` pair. |
| **Mutable identity** | `object_id` and `object_type` are immutable after creation. |
| **Synchronous execution dependency** | Object operations must not block on execution. Execution is async. |
| **Orphaned relationships** | When an object is archived, its relationships must be explicitly resolved (maintained, transferred, or severed). |

## V. Inheritance Model

```
                        ┌─────────────────────────────────────┐
                        │       Living Object (abstract)        │
                        │   Universal Capabilities (#1–12)     │
                        └─────────────────────────────────────┘
                                       │
                        ┌──────────────┴──────────────┐
                        │                             │
               ┌────────────────┐           ┌──────────────────┐
               │ Simple Object  │           │  Complex Object   │
               │ (no optional   │           │ (may activate     │
               │  capabilities) │           │  optional caps)   │
               └────────────────┘           └──────────────────┘
                                                   │
                                    ┌──────────────┼──────────────┐
                                    │              │              │
                              ┌─────────┐   ┌─────────┐   ┌─────────┐
                              │ Domain  │   │ Domain  │   │ Domain  │
                              │ Object  │   │ Object  │   │ Object  │
                              │ Type A  │   │ Type B  │   │ Type C  │
                              └─────────┘   └─────────┘   └─────────┘
```

- **Simple Object**: An object that only uses universal capabilities (Identity, Reality, Timeline, Relationships, Lifecycle, Memory, Health, Permissions, Searchability). Example: a Tag, a Label, a Category.

- **Complex Object**: An object that activates one or more optional capabilities. Example: a Proposal (may have Conversation, Commitments, Execution, Files, Communication).

- **Domain Object**: A Complex Object specialized for a specific business domain. The specialization is data, not code. Example: a `Proposal` with lifecycle stages `Draft → Sent → Under Review → Accepted/Rejected`.

## VI. Implementation Impact on EP-01-R2

The 5 missing core capabilities from EP-01-R2 are now mapped to this contract:

| EP-01-R2 Missing Capability | Living Object Contract Coverage | Status |
|---|---|---|
| **Create object** | **Universal capability #1 (Identity)** — object creation is the act of assigning identity. Not a feature. An inherent object behavior. | ✅ Removed from feature backlog. Object creation is a universal behavior. |
| **View object detail** | **Not a capability.** A Living Object does not define its own detail view. The UI renders objects through the canonical Living Object Card, which displays all universal capabilities. | ✅ Removed. Detail view is UI, not object behavior. |
| **Search** | **Universal capability #9 (Searchability)** — every object is searchable by definition. No separate search feature needed. | ✅ Removed from feature backlog. Searchability is universal. |
| **Task management** | **Optional capability #14 (Commitments)** — tasks are commitments on an object. Not a separate feature. | ✅ Removed. Task management is an expression of commitments. |
| **AI chat** | **Optional capability #13 (Conversation)** — AI chat is conversation around an object. Not a separate feature. AI observations are universal (#7 Cognition). | ⚠️ Reconciled. AI observations exist. Conversation is optional. |

**Result:** All 5 previously identified "missing capabilities" are either:
- Universal capabilities that already exist in the architecture (Identity, Searchability)
- Optional capabilities that follow from the contract (Commitments, Conversation)
- UI concerns that don't belong in an object contract (View detail)

**No additional implementation is required for EP-01 beyond what already exists in the canonical Living Workspace.** The perceived gaps were feature-oriented thinking applied to an object-oriented system.
